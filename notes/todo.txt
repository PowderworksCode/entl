## dialect.rs now covers Zig, and the retry guard turned out to be load-bearing

Uncommitted on 08-03, in this tree. `dialect.rs` was Rust-only; it now has a
per-language table and a second KIND of rewrite. Measured against Bun v1.3.14
(1,292 .zig files) through the checked-in zig pack.

Cowbird had independently built the same idea outside entl — `parse-patches.json`
plus `analysis/parsepatch.rs`, seven literal find/replace pairs keyed by file
path, length-preserving for the same reason. Both mechanisms were running in the
same process on the same bytes, because cowbird calls `LoadedParser::parse`. This
absorbs the general half.

### What was measured, so nobody re-derives it

    baseline              94 files rejected   39,636 declarations
    entl policy           88 files rejected   39,691 declarations   6 rewritten
    unconditional         90 files rejected   39,680 declarations  97 rewritten

Baseline reproduces cowbird's own measured 94 exactly, which is what says the
harness was reading the same thing.

THREE THINGS THE REASONING GOT WRONG BEFORE THE CORPUS WAS ASKED. Each was
predicted the other way in the write-up that proposed this:

  1. THE PATCH TABLE IS NOT A DESCRIPTION OF THE DEFECT. It is a description of
     the seven places where the defect happened to destroy a top-level
     declaration. Bun has the same construct in at least five spellings —
     `E!if`, `[N]if`, `[]if`, `?if`, `name: if` — and `: if` alone occurs 159
     times. A rule written against the position rather than the spelling finds
     `install/PackageInstall.zig`, which the patch table MISSES. 88 rejected
     against cowbird's 89.

  2. A TEXT PATTERN OVER-FIRES, AND THE MISFIRE IS DESTRUCTIVE. Applied
     unconditionally the way cowbird applies its patches — at read time, kept
     regardless — it fires on 97 files and only 6 need it. Two of the other 91
     are actively damaged, and BOTH PARSED CLEANLY BEFORE:

       sql_jsc/postgres/types/tag_jsc.zig   0 -> 18 errors,  15 -> 4 declarations
       sql_jsc/mysql/MySQLValue.zig         0 ->  5 errors,  18 -> 18

  3. SO THE GUARD IS THE FEATURE, not the table. `ParserRuntime::parse` rewrites
     only a tree that ALREADY has an error and keeps the retry only when it is
     completely clean. That is what turns a heuristic that loses 11 declarations
     into one that cannot lose any: neither damaged file is eligible, because
     neither failed. Entl's policy also BEATS unconditional rewriting outright —
     88 rejected against 90, +55 declarations against +44 — which is not what
     "apply more rewrites" intuitively predicts.

     This is the argument for entl owning the mechanism at all. It is not that
     entl is the tidier home; it is that cowbird's apply-always model has no
     place to put this rule safely.

### A second kind of rewrite, and why `narrowed` exists

Blanking `const` out of `const trait` leaves what the code SAYS intact. Choosing
a branch of `if (cond) A else B` does not: the signature is now narrower than
the file's. parse-patches.json says the same thing about its own data — "these
five signatures read as narrower than they are ... must not be fed to a model as
one" — and had nowhere to put it.

`Rewritten::narrowed` and `ParsedFile::rewrites_narrowed` carry that distinction
to consumers. Spans are correct either way, because byte length is still
preserved; the SOURCE TEXT at that span is not the author's. A consumer that
locates declarations is unaffected. One that quotes them is not.

## Parser-pack queries for the discarded-error check

Infact's `infact-rust-errors` recognizes discarded-error forms (`let _ =`,
`.ok()`, `Err(_)` arms, `Ok(..)` bindings, `filter_map(Result::ok)`,
`.unwrap_or*`, `map_err(|_| ..)`, `unwrap`/`expect`) by matching Rust
tree-sitter node kinds in Rust code. The FACTS are already language-neutral —
`DiscardForm`, `Containment`, `Certainty`, and `Reach` name no Rust concept —
so only recognition is language-bound. Every language has the same policy in a
different spelling:

  - TS/JS  empty `catch {}`, `.catch(() => null)`, unawaited promise, `void f()`
  - Zig    `catch {}`, `catch unreachable`, `_ = f()`
  - Go     `_ = err`, an `if err != nil {}` with an empty body

SPIKED AND VERIFIED against the checked-in rust pack (wasm grammar, ts 0.26).
Every recognizer currently written in Rust is expressible as a query. The
results, so nobody has to re-derive them:

  - `Query::new` compiles fine against a wasm-loaded `Language`.
  - The anonymous `_` pattern is matchable as a quoted node:
      (let_declaration pattern: "_" value: (call_expression)) @d
    matched `let _ = w()` and not `let x = w()`.
  - Predicates work: `(#eq? @m "ok")` matched `.ok()` and not `.unwrap()`.
  - THE ONE THAT MATTERED. Queries have no negation, and half the forms turn on
    the ABSENCE of a binding (`Err(_)` vs `Err(e)`, `|_|` vs `|e|`). A quantified
    capture solves it — the capture is simply missing from the match:
      (tuple_struct_pattern type: (identifier) @t (identifier)? @bind)
    `Err(_)` produced [d, t]; `Err(e)` produced [d, t, bind]. Same trick
    separated `map_err(|_| X)` from `map_err(|e| X(e))`.
    So the pack declares, per form, which captures must be ABSENT. That stays
    data; no per-language Rust.

[x] Load `queries/*.scm` from parser packs   -- DONE
    - `ParserPack` reads the sources at pack load; `ParserRuntime::load`
      compiles them against the loaded grammar. A query that does not compile
      fails the load, and naming a query a pack does not ship is an error
      rather than an empty result.
    - `LoadedParser::matches(name, file)` returns matches with named captures;
      `QueryMatch::has` reads capture ABSENCE, which is the negation substitute.
    - `ParsedRepository.parsers` now carries the loaded parsers by pack id,
      because a compiled query belongs to the grammar it was compiled against
      and so cannot live on the shared `ParserPack`.
    - `ParserPack::queries_sha256` digests the query set.

[x] Wire `queries_sha256` into `ParseProvenance` / `InputEvidence`   -- DONE
    - `ParseProvenance.queries_sha256` is populated at parse; every one of the
      six `InputEvidence` construction sites across Infact carries it through.
    - The compiler-observed path (`infact-rust-effects::observed`) writes empty:
      no parser pack and no queries were involved, which is a real distinction
      rather than a missing value.
    - `#[serde(default)]` on the new field, so evidence serialized before it
      existed still reads. Covered by a test in `infact-core`.
    - The property that matters is tested in entl: two packs with the SAME
      grammar and DIFFERENT queries must not carry identical provenance.

[ ] Express discard forms as `queries/discards.scm`
    - One capture per form, named after the `DiscardForm` variant:
      `@discard.let-underscore`, `@discard.ok`, `@discard.err-arm`, ...
    - A `@containment` capture on the enclosing callable's return type.
    - Per-form `absent = ["bind"]` in `parser.toml` for the negation cases.

NOT expressible as queries — these stay per-language data in `parser.toml`:
  - `Certainty`. `.ok()` proves a Result; `.unwrap_or_default()` reads the same
    on Option. Which forms are provable is a fact about the language's stdlib.
  - The query-result exclusion list. `binary_search*` and `Path::strip_prefix`
    return `Result` where `Err` is an ANSWER ("not present", "not under this
    prefix"), not a failure. Reporting those buries the real findings — it was
    ~10 of the first 75 findings. Every language has its own such list.
  - Return-type classification. Deciding `Result` vs `Option` vs neither from
    the captured type text is a per-language name list, not a query.

STAYS RUST regardless of any of the above (~400 of the 744 lines):
  the call graph, `resolve_reach`/`search_upward`, fact assembly, provenance.
  Reach is a graph search, not a pattern match. Moving recognition to data
  SHRINKS this crate to roughly a query-driven front end plus the graph; it does
  not remove it.

`collect_callables`, `repository_module`, `source_span`, `node_text`, and

                      closure). Each returns its OWN crate's Error, so sharing
                      it needs a shared error type or a generic parameter.
  node_text           FIXED 08-02. effects indexed `&source[start..end]`,
                      which PANICS on an out-of-range node; errors uses
                      `source.get(range)?`, which returns None. effects has
                      adopted errors' version. The same slice panic was also
                      present in effects' function-header read and got the
                      same treatment; `infact-rust-behaviors` was already safe.
  simple_type_name    SETTLED 08-02 on effects' spelling: `Bar`, not
                      `&mut Bar`, for `impl Trait for &mut Bar`. A reference
                      type is not usable as a `{module}::{implementation}::
                      {name}` path segment, which is the only thing this feeds.
                      errors' `rsplit("::")` version is gone. The note said
                      tests would not decide this because neither crate covered
                      the divergent shapes — errors now has one that does
                      (`names_an_impl_self_type_without_its_decoration`,
                      covering reference, qualified-path, and generic self

                      NOT unified into shared code: the two crates still each
                      carry their own copy, deliberately, per the item below.
  collect_callables   NOT DUPLICATED. Effects-only. Errors has its own `walk`,
                      which interleaves containment, test detection, and
                      discard inspection with the traversal — different needs,
                      not a copy.

## entl-rust-mir is outside every automated check

## The 77% generic gap — MEASURED, and one route is ruled out

Measured 08-02 over five real crates built with the driver as RUSTC:

    functions skipped for want of an instance   2,325 of 3,014   77.1%
    items whose body was read at all              763 of 3,384   22.5%
    per crate: serde_core 85.8%, quote 23.3%, proc_macro2 13.7%

The spread is the result. A concrete crate loses ~14%; a generics-heavy one
loses ~86%. Coverage is not a number, it is a property of the code observed.

WHAT IS ACTUALLY LOST. Calls INTO a generic are recorded, with the
instantiation — `instantiates -> generic_caller::<u8>`. Calls INSIDE it are
not. The graph is TRUNCATED AT EVERY GENERIC BOUNDARY: edges arrive at a
generic function and stop. For effect propagation that is the worst shape,
because reach ends silently at exactly the functions that forward work.

[ ] RULED OUT: reading the polymorphic body via `CrateItem::body()`
    It works, and on a fixture it is exactly right — 3 edges become 10, gaps go
    to zero, and the seven new ones label cleanly as `unmonomorphized`.
    It does NOT survive real code. proc_macro2 and serde_core both abort in
    `normalize_erasing_regions.rs:201`, and coverage went DOWN (5 crates to 3)
    because the driver now dies earlier than it used to.
    The abort is NOT `Instance::resolve` — that is guarded now. It is reading
    the callee operand's own type: `Ty::kind()` normalizes eagerly and cannot
    handle the unresolved projections a polymorphic body carries. That is a
    rustc_public limitation, not something a caller can guard around.
    The experiment is kept at scratchpad/experiment-polymorphic-body.rs.
    Do not re-derive this; it costs a full driver build and two crate builds.

[ ] NEXT ROUTE TO TRY: walk monomorphized instances rather than local items
    `all_local_items()` yields the generic item, which has no instance. The
    compiler also produces the INSTANTIATIONS it actually generated, and those
    have bodies, resolved destinations, and no normalization problem — the
    schema needs nothing new for them. It cannot see a public generic API the
    crate never calls itself, so it will not reach 100%, but it covers the
    generics a scanned repository actually uses, which is the case that
    matters. Measure the coverage it reaches before building on it.

[ ] It panics reading syn's MIR
    rustc_public/src/mir/body.rs:1057 during `visit_body`, on
    syn 3.0.3. Five crates observed cleanly first (proc_macro2, quote,
    serde_core, unicode_ident, a build script), then a hard stop. Not
    diagnosed. A driver that aborts the build on one crate cannot be a
    drop-in RUSTC, so this gates the same task.

[ ] Decide whether it should carry the lint denials
    A non-member crate needs them written into its own `[lints]` table; it
    cannot inherit `[workspace.lints]`. Straitjacket's `error-discard` rule
    DOES cover it (the scan is path-based, not cargo-based), so the discard
    forms are policed. The panic/must-use lints are not.

## Parser setup was being repeated per file — FIXED, and it was fleet-wide

`LoadedParser::parse` built a fresh `Parser`, a fresh `WasmStore` and called
`set_language` on every call. That is setup, it does not depend on the file, and
it dominated every consumer that parses more than one thing.

Measured with the same loaded parser, before and after:

    19-byte source      123 ms  ->  0.087 ms
    40,564-byte source  210 ms  ->  85 ms

Nearly all of the smaller number was setup being repeated, which is why the two
were so close together despite a 2000x difference in input. What remains is
parsing, and it is now proportional to the file.

`load` already built a `WasmStore` to read the grammar out of and then dropped
it. It now keeps a parser configured with that store and language, behind a
`Mutex` because `Parser::parse` needs `&mut` while consumers hold a
`LoadedParser` by reference and `ParsedRepository` holds several in a map.

WHY IT MATTERED EVERYWHERE: `parse_repository` loads one parser per language and
reuses it — that part was always right — but it calls `parse` once per file, so
`infact-duplication`, `infact-rust-effects`, `infact-errors` and
`infact-rust-behaviors` all paid roughly 123ms x file count. About two minutes
of dead time on a thousand-file repository, in every analyzer, since the wasm
parser landed.

Found by profiling a TypeScript scan that would not finish in eleven minutes;
with this it completes in seventy-eight seconds. Nobody would have found it by
reading the code — the call looked exactly like the one that was already
correct.

If a consumer ever wants PARALLEL parsing it should hold one `LoadedParser` per
thread rather than contend on this lock. Nothing in the tree parses concurrently
today, so the lock costs nothing now.

## A TypeScript provider now exists

`providers/typescript/observe.mjs` runs the TypeScript checker and emits
`SemanticObservations`; `entl-ts-observe` drives it. Measured on a 1,047-file
monorepo: 18 seconds, 1.9GB, 8,547 definitions, 88,013 calls, 47,012 types, 609
gaps, every span repository-relative.

`entl-semantics` needed NO change. The schema was written with TypeScript in
mind — `EntityId` documented "a TypeScript file and qualified name", `CallEdge`
already held several destinations, `TypeRef` already declined to reconcile
structural types with traits.

Unlike `entl-rust-mir` this needs no pinned toolchain and no compiler-private
crates, so it is an ordinary workspace member covered by `cargo test` and
`cargo clippy` rather than sitting outside every automated check.

Entities are minted from DECLARATION SITES, not `getFullyQualifiedName`. That
name was measured to embed absolute filesystem paths for anything a module
exports, to spell the same symbol differently depending on whether it is
exported, and to call every anonymous object type `__type`. None of that
survives being compared across machines.
